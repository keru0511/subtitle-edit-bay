# 実音声による文字起こしCI

`.github/workflows/transcription-accuracy.yml` は文字起こし関連のPRで、固定した日本語実録音をWhisperXの実モデルで認識します。通常のモックテスト、既存の電子音スモークテストとは別の検証です。

## 実行条件

Windowsのホストランナー、Python 3.10、製品のCPUロックファイル、`large-v3`、日本語、CPU int8を使用します。モデルの初回ダウンロードを含み、通常の単体テストより時間がかかります。新しいGPUランナーや認証情報は不要です。処理中に失敗した場合も成功扱いにせず、認識ログを成果物へ残します。

PRではイベントのbase SHAとマージ候補を別checkoutに読み込みます。手動実行では`compare_ref`で比較対象を指定できます。評価器と固定素材は両方の認識に同じものを使い、各checkoutの製品用コマンド生成関数と既定VAD値を読み込んで実行します。認識結果のキャッシュは使いません。WhisperX/PyTorchなどのバージョン、両checkoutのSHA、実行コマンド、音声ハッシュを記録します。

## 評価内容

参照文はKokoro Speech Datasetの提供メタデータです。この変更では録音を聴いて全文を照合していません。配布元の切り出しと注釈は自動処理のため、以下のCERは提供メタデータに対する値です。人が聴いて確定した正解に対する値としては扱いません。

- 配布元の参照文に対する文字誤り率（CER）、挿入・脱落・置換の数
- 無音・雑音区間に出た文字数
- 語時刻の欠損、不正な字幕時刻
- 正解文字列との対応から求める、既知の発話区間からの時刻逸脱
- 処理時間（モデル読み込み・初回ダウンロードを含む参考値。速度比較の合否判定には使わない）

生のCERは全半角・英字大小・句読点・空白を正規化して計算します。合否用のCERは、後述する素材固有の5組の同等表記も揃えます。繰り返しを削除してスコアを良くすることはしません。全文が空なら脱落として失敗します。正しい文でも別の発話区間へずれれば失敗します。

合否の基準は `assets/asr_benchmark/manifest.json` に固定します。文字誤り率25%を超えた場合、旧版よりCER・挿入・脱落が悪化した場合、許容0.4秒を超えて発話区間外へ出た文字、時刻欠損、不正時刻がある場合はジョブを失敗させます。同じ結果で合格しても「改善した」とは扱いません。

公開固定素材の単語ごとの正解開始・終了時刻は用意できていません。録音配置区間からの逸脱と単語境界の誤差は別指標です。人手注釈を持つ録音は開始・終了の誤差と語尾短縮を採点し、未注釈は未検証と表示します。注釈形式と再推論不要の再採点手順は [単語境界の評価](TRANSCRIPTION_BOUNDARY_ANNOTATION.md) を参照してください。実際のゲーム実況への効果も、この小さな朗読素材では証明できません。

## 成果物とローカル実行

両版を独立したマトリクスジョブで実認識し、Ubuntuの集約ジョブで比較します。認識の片側が失敗しても、もう片側のログは保存します。音声ハッシュ・素材と判定条件・ライブラリ版・モデルのスナップショットが一致しない結果は比較を失敗させます。集約処理にWhisperXのインストールは不要です。

Actionsのサマリーに比較表を出し、`transcription-accuracy-<run id>` に比較レポート、`transcription-accuracy-baseline-<run id>` と `transcription-accuracy-candidate-<run id>` に各音声・認識JSON・実行コマンド・ログを14日間保存します。

同じランタイムを用意した端末では、次のように実行できます。

```sh
python scripts/benchmark_transcription.py --baseline-root ../baseline --candidate-root . --output out/asr-report
```

評価器の単体テストは通常のportable-unitグループに含めます。実認識ジョブには推論モックを使いません。

## 表記差と発言の欠落の区別

初回実行では生のCERは両版とも7.69%でしたが、「あとから→後から」の表記差が1文字の脱落として扱われました。そこで元の正解文と生のCERを保持した上で、固定素材に明記した5組の同等表記だけを揃えたCER・編集操作数を判定に使用します。詳細は [素材の表記差の扱い](../assets/asr_benchmark/README.md) を参照してください。合否の数値上限は変更していません。

## CIの時間と実行範囲

実行36130825670は合計8分6秒で、依存導入2分59秒、実認識2分58秒、pipキャッシュ保存58秒でした。この測定をもとに、pipのダウンロードキャッシュを導入済みCPU仮想環境のキャッシュへ置き換えています。

- OS・Windows系列・CPUアーキテクチャ・Pythonのビルド情報と実体パス・仮想環境の配置先・CPUロックファイル・ランタイム契約が完全一致する環境だけ復元します。Windows配布イメージの更新日だけでは無効化しません。部分一致の復元はしません。
- キャッシュ利用時も依存整合性と製品ランタイム契約を検証します。初回はハッシュ固定でインストールし、検証済み環境を保存します。pipキャッシュとの二重保存はしません。
- 認識結果はキャッシュせず、比較対象と変更後を別々のWindowsランナーで並列に毎回実認識します。モデルや評価素材を小さくして検証を省略する最適化は行いません。
- モデルキャッシュは転送コストを測定してから判断し、現段階では導入しません。
- 文書・評価器の単体テストのみの変更、GPU用ロックのみの変更では実認識を起動しません。認識実行コード・設定・CPU環境・音声・正解データ・評価器の変更は対象です。
- 同じPRの新しいpushは古い実行をキャンセルします。ジョブ全体は30分、各版の認識は10分で打ち切り、異常時に長時間占有しません。

キャッシュの効果はコールド実行と同じコミットのウォーム実行を区別して測定します。初回保存の時間を含めずに短縮を断言しないようにします。

### 旧版・新版の並列実行

初回キャッシュ作成を含む実行36131943691のattempt 1は6分57秒でした。認識は旧版79.56秒、新版91.71秒と直列だったため、両版を別ランナーへ分けます。同じCPU上で推論プロセスを競合させず、比較処理だけを後段で実行します。片側失敗・結果欠落・条件不一致は合格にしません。

別ランナーでは環境復元とモデル取得が二重になるため、経過時間の短縮と総ランナー時間の増加は分けて評価します。モデルの小型化、検証音声の削減、認識結果の再利用は行いません。

[並列実行36133892416](https://github.com/keru0511/subtitle-edit-bay/actions/runs/36133892416) は全ジョブ成功しました。最初のジョブ開始から比較完了まで5分28秒、総ランナー時間は8分17秒です。旧版ジョブはキャッシュ利用で2分50秒、新版ジョブはキャッシュ不一致による新規導入・保存込みで5分19秒、集約ジョブは8秒でした。キャッシュ利用側は復元27秒・ランタイム検証16秒で、並列化前の再実行でも復元25秒・検証17秒でした。認識本体は77.93秒と101.85秒で、精度指標は先行実行と一致しました。

直列の初回実行6分57秒に対して今回は待ち時間が短くなりましたが、総ランナー時間は増えています。両側ともキャッシュ利用した全体時間は未測定です。単回・キャッシュ条件が異なる測定のため、安定した短縮率や上限時間を保証するものではありません。並列化前のキャッシュ利用再実行は新しいpushでキャンセルされ、環境準備の時間だけを採用しています。

### キャッシュの安定化

配布中のWindowsイメージが20260907版と20260922版に分かれ、片側だけキャッシュを失っていたため、v2キーからImageVersionを外しました。ImageOS（Windows系列）・CPU・Pythonのビルドとパス・仮想環境のパス・依存定義はキーに含めます。仮想環境を別のパスやPythonへ流用する部分一致復元は行いません。

復元のたびにpip checkと製品ランタイム契約（固定パッケージ版、重要モジュールのimport、FFmpeg/ffprobeの動作）を検証します。復元環境が壊れていた場合は一度だけハッシュ固定の依存から再構築し、同じ検証を再実行します。再構築・再検証に失敗したら認識へ進まず失敗させます。定義そのものの不整合は再構築で隠しません。

Actionsのキャッシュは同じキーを上書きできないため、壊れた既存キャッシュが繰り返し再構築を起こす場合は対象キャッシュを削除して再作成します。サマリーのrestored / installed / rebuiltで区別できます。キー変更後の最初の実行はキャッシュを新規作成します。モデルと認識結果のキャッシュ方針は変更していません。

## 聞き取り条件を増やした120秒の評価

元の70秒の配置を維持したうえで、同じ実録音に音量低下・発話中の雑音・合成背景音・帯域制限を施した4発話と、声のない合成音の負例を追加します。仕様と未検証範囲は [素材の説明](../assets/asr_benchmark/README.md#聞き取り条件の追加) を参照してください。

旧版・新版はそれぞれ120秒の1ファイルを認識します。同じ元録音4件を2回使ったクリップ長の合計は約31.0秒で、残りは無音・固定雑音・合成音です。従来70秒のクリップ長合計は約15.5秒でした。クリップ内の有声音の長さは測定していません。条件ごとにモデルを読み直すジョブやプロセスは増やさず、既存の2ジョブ並列化とランタイムキャッシュを維持します。入力は70秒から120秒になるため認識時間は増えます。実行時間は実CIで記録し、同じと断定しません。

全体の指標に加えて5条件を独立に採点・判定し、ある条件の悪化が別条件の改善で平均化されることを防ぎます。正解文・同等表記・上限値は従来どおりです。追加パターンで検出した時刻ずれに対し、CTCのblankを文字時間に含めない修正も加えています。このPRの最終差分では認識の生成設定・モデル・評価基準は変更しません。詳細は [初回認識の方針](TRANSCRIPTION_ACCURACY.md#無音を文字の持続時間に含めないctc時刻合わせ) を参照してください。

### 追加パターンで見つかった時刻逸脱（2026-09-25）

[実認識36138381663](https://github.com/keru0511/subtitle-edit-bay/actions/runs/36138381663) では両版の認識処理が成功し、比較の絶対基準で失敗しました。mainと変更後はともに生のCER 7.69%、同等表記統一後のCER 0%で、本文は一致しました。ただし次の語時刻が次の発話まで伸びています。

- 音量低下ケースの「る」: 76.834〜84.298秒（発話区間74〜77.436553秒）
- 合成背景音ケースの「す」: 96.972〜104.258秒（発話区間94〜97.541043秒）

最大逸脱は約6.86秒でした。条件別の区間内CERは時刻で文字を振り分けるため、本文の脱落がなくてもこのずれで悪化します。本文だけのCERと混同しないよう、レポートにも注記しています。

製品コードが同じmainでも再現する既存の課題です。評価上限を緩めたり、このケースを削除したりせず、再現用の評価追加として残します。この結果を受け、初回認識プロファイルv2でblankを区別したCTC経路を適用し、同じ素材と基準で再評価します。全体は初回環境導入・保存を含め6分19秒、認識処理は旧版152.59秒・変更後149.48秒でした。
